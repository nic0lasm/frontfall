# Security review, 0.9.9

A read-through of what the game server accepts from outside, the content security policy and the dependencies, done on `next` (commit 09ed16d, 3 November 2026) by reading the code. Nothing was run against a live server, so every finding below is a reading of the code, with the place to look. Reports of vulnerabilities go through [SECURITY.md](../SECURITY.md), not here.

**Result:** nothing of high severity. Two findings of medium severity, five of low, and a few notes. None is exploitable against the public server today in a way that exposes accounts or games; the two medium ones are about abuse of the email sign-in and about a default that is unsafe for self-hosters.

## Already in place

- Secret scanning and push protection are on for the repository, CodeQL runs on every push, Dependabot opens weekly updates (grouped, [dependabot.yml](../.github/dependabot.yml)), and `pnpm audit` on `next` reports no known vulnerability.
- The server limits connections, messages, orders and sign-in links ([server.md](server.md#limits)).

### Since the review

Done before v0.9.9: the mailbox budget of sign-in links (the first medium finding), `X-Content-Type-Options: nosniff` on the JSON replies and the sign-in replies, and a cap of 100,000 addresses on `AddressRate`. Done for v1.0: `FRONTFALL_ORIGINE` takes a comma-separated list and its absence is documented; built assets (`/assets/`, named by content hash) are kept in memory after the first read, up to 32 MiB; the cookie that ties a sign-in link to the browser is built and switched on with `FRONTFALL_LOGIN_BIND=true`. Left off by default because it also refuses a link opened in another browser or app, which is how many people open a mail from their phone; turn it on once that trade-off is accepted. The default of `trustProxy` stays `true`: `compose.yaml` now sets `FRONTFALL_TRUST_PROXY` explicitly, and the default can become `false` once the production compose file sets it too.

## Content security policy

The server sends `default-src 'self'; img-src 'self' data: blob:; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. Reading what the client loads: scripts, modules, workers and fonts are all same-origin; the only inline script is JSON-LD data, which is not executed; there is no `style` attribute, no `<style>` element and no inline style set through the DOM attribute; the `blob:` addresses are used for downloads; network calls are same-origin `fetch`, `sendBeacon` and `WebSocket`; and the message validation runs without `eval`. The policy therefore breaks nothing, needs neither `unsafe-inline` nor `unsafe-eval`, and leaves no gap: every unlisted fetch directive falls back to `'self'`, so writing them out would add nothing.

On the public server Caddy replaces this policy for `/frontfall*` with a longer one (explicit `script-src`, `connect-src` with `wss://nclsmgr.com`, `worker-src`, `font-src`, `style-src`, `upgrade-insecure-requests`). `upgrade-insecure-requests` is rightly absent from the server's own policy, which would break self-hosting over plain `http://`. Older browsers may not count `ws:` under `'self'`; this was not tested in a browser.

## Dependencies

- **Server, in production:** `zod` and `nodemailer`, none with dependencies of its own; HTTP and WebSocket come from Bun itself (`Bun.serve`). They are bundled into `server.mjs`, and the image carries no `node_modules`, so supply-chain risk is limited to the build. `nodemailer` is the largest and the only one near user data (the destination address, filtered by a strict pattern before use; file and URL access are disabled).
- **Client:** `three`, a font package and the two internal packages. All are bundled.
- Dependabot and `bun audit` cover advisories. This review did not look up advisories itself.

## Checked and found sound

- **WebSocket messages:** at most 1024 bytes, validated with strict schemas, binary frames refused when malformed, orders bounded, reconnection tokens of 128 bits, game numbers of 72 bits.
- **Names:** length bounded, normalised, restricted to an Unicode allow-list; reserved names, addresses and invisible characters refused.
- **Static files:** `//`, `\`, a null byte, bad percent-encoding and any path leaving the root are refused.
- **Administration routes and `/metrics`:** reachable only from the host itself, with no proxy header, no `Origin` and a local `Host`; Caddy answers `404` on them as well.
- **Sessions:** HMAC-signed cookie compared in constant time, secret of at least 32 characters, `HttpOnly`, `SameSite=Lax`, `Secure` over HTTPS; OAuth with PKCE, a signed `state` and a fixed redirect; every state-changing route needs `POST` and the right `Origin`.
- **Email links:** a 256-bit token in the page fragment (never in logs or `Referer`), stored hashed, single use, valid 15 minutes; the same answer whether the address exists or not; no header injection in the address; TLS to the mail server.
- **Logs:** one JSON line per event, addresses hashed with a random key, client error messages scrubbed and capped.
- **Memory:** bounded inboxes for usage reports, pending links and request bodies; header and request timeouts.

## Not checked

The doubled headers of Caddy in a running proxy, `ws:` under `'self'` in older browsers, recent advisories of the dependencies, the engine's own validation of orders (the server only checks their form and relays them), and any dynamic test against a running server.
